The pushwork daemon

A background process that runs pushwork's commands, keeps one connection open per sync server across them, and is checked and restarted by the CLI on every command.

chee6 November 2026draftbuilds on One store per machine

What changes for someone using pushwork

  • Commands look and behave the same. The first one starts a daemon in the background; later ones reuse it, and reuse its open connections to sync servers.
  • pushwork daemon status shows whether it's running, its pid and version, and which servers it holds connections to. pushwork daemon stop stops it.
  • --no-daemon runs a command in the CLI's own process, as before. It stops a running daemon first (see "the shared node" for why).
  • The daemon logs to ~/.pushwork/daemon.log. It exits by itself after 10 minutes with no commands, or when its home directory disappears.

Every command checks the daemon

The CLI connects to the daemon's socket and says hello with its version. The version is the package version plus the modification time of the installed dist/daemon.js, so a rebuild or an upgrade counts as a new version.

    What the CLI does before and during one command, in each situation.

    The daemon isn't restarted automatically in the middle of a command: the command could have committed and partly synced, and running it twice is a decision for the person. Every later command finds the daemon gone and starts a new one.

    Where it lives

    ThingWhere
    Socket (macOS, Linux)~/.pushwork/daemon.sock. If that path is longer than 100 bytes (the limit is 104 on macOS), /tmp/pushwork-<uid>/<hash of home>.sock in a directory created with mode 0700. Either way only the user can connect.
    Socket (Windows)The named pipe \\.\pipe\pushwork-<hash of home>.
    Pid~/.pushwork/daemon.pid, used to kill a daemon that doesn't answer.
    Log~/.pushwork/daemon.log, the daemon's stdout and stderr (truncated at each start).

    One daemon per home directory, so test suites and separate users each get their own. It starts as node dist/cli.js daemon run, detached, with the environment of the command that started it (including DEBUG).

    How commands reach it

    The CLI keeps its argument parsing and all of its output. Only the calls into src/pushwork.ts move: each is sent to the daemon by name with its arguments, and the result comes back. Messages are CBOR (already a dependency) with a 4-byte length prefix, so bytes in diff results and Maps survive.

    • Functions in the arguments become handles the other side can call. Progress reports, warnings and clone's "run this strategy?" prompt (which passes a viewCode function back) work across the socket without special cases.
    • An error thrown in the daemon is rethrown in the CLI with the same message, so exit codes and output don't change.
    • Only the functions the CLI imports today are callable. Pure helpers (plural, constants) stay local.

    Two commands at once

    The daemon runs commands concurrently, the way separate processes run today: commands in different checkouts share the node, and the checkout lock from project 1 still refuses a second command in the same checkout, now naming the daemon's pid. The one exception is migrate, which replaces the shared node afterwards: it waits for running commands to finish, holds new ones back while it runs, and lets them go once the new node is in place.

    The shared node

    The daemon holds one Subduction node on the machine store, with one connection per sync server. Docs gains a hub option: with it, Docs uses the hub's node and allowlist, asks the hub for the connection to its server, and leaves the connection open when it closes.

    Every write to the store in the daemon goes through the hub's node. A Subduction node keeps documents it has touched in memory and never rereads them. A spike confirmed it: after a second node wrote a commit to the same store, the long-lived node's next sync sent nothing (totalSent 0), with maxResidentTrees unset and at 1. With every write going through one node, 40 alternating offline saves and online syncs with compaction between them ended with the server holding exactly the local document.
    • Offline commands in the daemon use the hub's node too, without a connection.
    • migrate imports blobs straight into the store, so the daemon replaces its hub (new node, connections re-dialled) after a migrate.
    • --no-daemon stops a running daemon before it starts, so a daemon never holds a stale view of what another process wrote.
    • Keyhive repos keep a node of their own per command, as in project 1. Keyhive's adapters register frame handlers and listeners on the node and never remove them; on a shared node they would pile up across commands. Their documents use 32-byte ids, so they never overlap with the hub's.
    • Docs.pull() still uses a throwaway node: it only ever adds commits the server already has, so the hub missing them costs a repeat download, nothing more.

    Connections

    The hub keeps a map from server URL to peer. Before handing out a peer it checks getConnectedPeerIds(); a peer that has dropped is dialled again, with the same 10 second timeout as today. The allowlist is the hub's, shared by every command: a document synced with a server by any command stays allowed with that server.

    Testing

    LevelWhat it checks
    unit, rpcCalls round-trip Uint8Array, Map and nested objects; a function argument can be called back, including one inside an object passed to a callback; errors keep their message.
    unit, hubTwo Docs on one hub open one connection to a server; a connection the server dropped is re-dialled; closing Docs leaves the connection open; the shared-node scenario from the spike (writes from one command are sent by the next).
    integration, daemonIn its own home: two syncs open one connection to a counting server; daemon status reports a pid; after kill -9 the next command works with a new pid; a newer dist/daemon.js mtime restarts it; --no-daemon runs without one and stops a running one; a daemon exits when its home is deleted.
    whole suiteEvery existing integration test runs through the daemon, since it's the default. The test setup stops the shared home's daemon at the end.

    Out of scope

    • Keyhive repos on the shared node (needs keyhive's adapters to be removable).
    • Keeping keyhive archives open between commands.
    • Re-running a command automatically after the daemon dies mid-command.
    • Starting the daemon at login (launchd, systemd).
    • Restricting the Windows pipe beyond its default access control.
