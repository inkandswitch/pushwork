One store per machine

pushwork moves every document into one store at ~/.pushwork/storage. Each checkout keeps only a record of the heads it last saw. This is the groundwork for a background daemon that keeps one connection open per sync server.

chee5 November 2026draft for reviewbranch pushwork-server

Where this fits

The goal is a background process that keeps a long-running connection open to each sync server, restarts itself when it falls over, and is checked by every command, so networked commands stop opening a connection each time.

A Subduction connection belongs to a node, and a node belongs to one storage. Today every repo has its own storage in .pushwork/storage, so a daemon could only share a connection per repo, not per server. To share connections per server, the storage has to move out of the repos first. The work splits into two projects, each with its own spec and plan:

  1. Machine-wide store (this spec). One store, per-checkout heads, server isolation. The CLI still runs every command in its own process.
  2. Daemon (next spec). One process holds the store, one Subduction node, a connection per sync server and the open keyhive archives. The CLI becomes a thin client that starts it, checks its version and health, and restarts it.

The store

Every document lives in ~/.pushwork/storage, in the same FsStorage layout as today (src/storage.ts). .pushwork/storage goes away.

The sent/ records (the fragment heads a server is known to hold) already name their server, but there is one file per document, so a second server overwrites the first. They become sent/<server-hash>/<doc-id>, so one document can be tracked against several servers.

The store only grows. Deleting a checkout leaves its documents behind. A pushwork gc is out of scope.

Each checkout keeps its own heads

Today a repo's saved state is whatever is in its own storage: readSaved decodes the live documents (src/pushwork.ts:1331). With a shared store, two checkouts of the same URL on one machine would share that state. When one syncs, the other's working tree stops matching, its status shows the change as a local revert, and its next sync pushes the revert.

So each checkout gets .pushwork/heads.json, mapping every document id it uses (root, folders, files) to the heads it last saw. It works like git's index: the store holds every version, and this file says which version is this checkout's.

How Docs uses the map

Docs opens with the map as its base. Shapes don't change; they only see find and change.

  • find(url) returns A.view(doc, base) for a document in the map, and the live document otherwise (new docs, or ones just fetched).
  • change(url, fn) calls A.changeAt(doc, base, fn) and moves that document's base to the new change's heads. An edit made against an old base merges with other checkouts' edits as a concurrent change. updateText diffs against the text at base, so a stale checkout never reverts newer edits.
  • heads() and pin() read the base, so pushwork heads and artifact pins show this checkout's view.
  • advance() moves every base to the live heads. It is the "merge in everyone else" step.

With one checkout per URL, base always equals live heads and changeAt behaves exactly like change, so the common case doesn't change.

What each command does with it

CommandReadsThen
status, diff, cut, headsbaseChanges nothing.
savebaseCommits at base and writes heads.json. Doesn't pull in other checkouts' changes: like the server, the store is something you merge from on sync.
syncbaseCommits at base, syncs, calls advance(), writes the merged tree to disk, writes heads.json.
clone, track, init, mergeliveRecords the live heads.

If a base head is missing from the store (for example, after someone deleted ~/.pushwork/storage), sync fetches from the server first, and other commands fail with a message that says so. That's no worse than deleting .pushwork/storage today.

Keeping documents off the wrong server

A node connected to server X now sees every document on the machine. Subduction's default policy allows everything, so X could fetch documents that belong to a repo synced with Y. Each Docs node gets a deny-by-default Policy built on one rule:

A peer may exchange a document with us only if this run started a sync of that document with that peer.
  • Docs.syncDoc records (peer, document) in an allowlist before it calls syncWithPeer.
  • authorizeFetch and filterAuthorizedFetch let a peer read only allowlisted documents.
  • authorizePut lets a peer write only allowlisted documents, so a server can't drop unrelated documents into the store.
  • Ephemeral subscribe and publish are denied; pushwork doesn't use them. Keyhive frames go through the frame handler, which is separate.
  • Documents keyhive syncs (group and membership docs) join the same allowlist. They get no separate exception.
  • An ESLint no-restricted-properties rule bans syncWithAllPeers, fullSyncWithPeer, fullSyncWithAllPeers and the add* calls in src/. Each of them talks to every connected peer: harmless today, a leak once the daemon is connected to several servers.
Repo P syncs with server X, repo Q with server Y, and shared.png is linked from both. A red chip is a document on a server it doesn't belong to. Try X asks for everything under each policy.

A document reaches a server only when you sync a repo that links to it from that server. A file linked into two repos on two servers goes to both, which is what linking it means. When you switch a repo's syncServer, its next sync goes to the new server and nowhere else.

Not yet verified: whether the policy hooks fire for data we send during a sync we start. The allowlist covers either case, and a test pins it down (see Testing).

Concurrent commands

Until the daemon exists, several pushwork processes can share the store at once.

ConcernApproach
Two processes writing the storeAlready safe. FsStorage writes are content-addressed, and each blob is renamed into place before its meta.
Compaction deleting a blob another process is readingCompaction deletes only once a fragment covering the blob is on disk. A read that finds a file gone lists the document again and retries once, and the retry finds the fragment. No store-wide lock.
Two commands in one checkoutA new .pushwork/lock, created exclusively and holding the pid. A lock left by a dead process is taken over; otherwise the command fails with "another pushwork is running here (pid N)". Nothing prevents this today, so it's also a small fix in its own right.
heads.jsonWritten to a temporary file, then renamed into place.
sent/ races between two processes syncing one document with one serverAccepted. A lost record only keeps a fragment as loose commits for longer, which costs bandwidth but not correctness.

Project 2 inherits two things: the allowlist becomes per peer across every running command in one node, and keyhive's single frame-handler slot (registerFrameHandler) needs a dispatcher, because keyline claims and releases it per command (src/keyhive/keyline/sync.ts:114).

Migration

The config version goes to 7. No fields change; the version moves because .pushwork/ means something different (no storage/, a new heads.json). Strict versioning stays: a v6 repo is refused with a message pointing at pushwork migrate. The current message says "from pushwork 2" (src/config.ts:80) and gets fixed for v6.

Step through pushwork migrate on a v6 checkout, offline. Highlighted lines are what the current step writes. Fail at this step shows what is left on disk if it stops there.
  1. Lock the checkout.
  2. Copy each document from .pushwork/storage into the machine store with saveBatchAll, skipping any already there. Going through the storage API rather than copying files means a half-finished migration can't leave a partial pair behind.
  3. Convert the old sent/ files, which record their server on the first line, into the per-server layout.
  4. Decode the tree at its live heads and write heads.json with every document's current heads.
  5. Move the old storage/ into .pushwork/pushwork_migration_backup_safe_to_delete/, as migrate already does.
  6. Write the v7 config.

If anything fails, the config stays at v6 and the old storage stays in place. Copies that already reached the machine store are harmless, because they're content-addressed. Repos older than v6 keep the existing path (attach("track")), which now writes into the machine store and records heads without extra work.

The changeset is a major bump, because existing repos have to run pushwork migrate. Open: fold this into the 3.0 prerelease instead.

design/sync.md, design/config.md and the layer diagram in design/README.md get updated to describe the machine store and checkout heads.

Testing

test/server.ts already runs a local Subduction server and accepts a Policy, so all of this runs without the network. The existing suites must pass unchanged; they already isolate ~/.pushwork with setHome.

Out of scope

  • The daemon. Project 2, with its own spec.
  • push: send local changes without touching the working tree. Deferred. The protocol has one-way LooseCommit and Fragment messages, but the 0.16.1 bindings expose them only as unacknowledged pushes to subscribers. Questions for Brooke: can a JS call push to one peer without reconciling, and does the server acknowledge a put or report a refused one?
  • pull: fetch, advance(), write to disk. Easy on top of this, but not asked for.
  • pushwork gc for documents no checkout uses.
